## Bcrypt or PasswordHasher (06-2026) 
## ps. ----Исправь на свое мнение-----
- Выбран: `BCrypt` (через `BCrypt.Net-Next`).
- Почему: 
   Не привязан к ASP.NET Identity:** Встроенный `PasswordHasher<TUser>` требует дженерик-класс пользователя (`TUser`), навязывая архитектуру Identity. `BCrypt` — полностью независимая утилита, работающая с чистыми строками.
   Сложнее взломать на видеокартах (GPU):** `PasswordHasher` под капотом использует алгоритм PBKDF2 (множество итераций SHA-256), который легко и дешево параллелится на фермах видеокарт. `BCrypt` использует алгоритм на базе Blowfish, требующий быстрой памяти процессора, что делает взлом на GPU крайне неэффективным.
   Стандартный межплатформенный формат:** Хеш BCrypt (начинается с `$2a$...`) стандартизирован и читается любым языком программирования (Go, Node.js, Python). У `PasswordHasher` проприетарный бинарный формат Microsoft в Base64.
   Простота в коде:** Для `BCrypt` не нужно регистрировать и прокидывать сервисы через DI — методы `HashPassword` и `Verify` вызываются статически в одну строчку.
## RateLimiter (02-08-2026)
	- Выбран: Fixed Window, partition by IP-адрес.
- Почему:
	Защита инфраструктуры от CPU DoS: Каждая проверка через `BCrypt.Verify` сжигает мс. работы CPU. Лимитер отбивает ответом HTTP 429 в Middleware, не доводя запросы до контроллера защищая CPU от истощения
	Совместимость с корпоративным NAT: Порог лимита выставляется с запасом (например, 100 запр/мин на IP выбрано с запасом, эмпирически не подбиралось, при появлении метрик пересмотрим)
	Всплеск на границе — это осознанно принятая цена за простоту и дешевизну Fixed Window. Он приемлем, потому что цель лимитера — не точное дозирование, а отсечение потока, способного положить CPU. 
Двойной всплеск на две секунды CPU не кладёт. Sliding Window решает эту проблему, но платит памятью на хранение отметок времени.
	Ограничение по IP не дает «уронить» сервер штормом запросов, но от подбора пароля к конкретному аккаунту не спасает — хакер просто будет менять IP-адреса.
Настоящая защита аккаунта — это блокировка учётки после нескольких неверных попыток ввода пароля. Эта фича пока у нас в в бэклоге.
- Отвергнуто:
	Партиционирование по логину: Требует буферизации и парсинга `Request.Body` до контроллера (уязвимость к RAM DoS через тяжелые JSON-пакеты), 
а также создает уязвимость Self-inflicted DoS (блокировка входа настоящему `admin` путем флуда его логином).
	Sliding Window / Token Bucket: Избыточны по памяти и ресурсам CPU. Для первичного базового забора инфраструктуры усложнение алгоритма не дает преимуществ при адекватно настроенном размере Fixed Window.
	Concurrency Limiter: Отслеживает только одновременные потоки, но свободно пропускает высокий суммарный RPS при быстрых запросах.

## JWT-token (12.08.2026)
   Вариант первый — сессия. При логине сервер генерирует случайный идентификатор, кладёт sessionId → {userId, role} в память или Redis, отдаёт клиенту cookie. 
На каждом запросе сервер по этому id лезет в хранилище и достаёт, кто пришёл.
   Ключевое свойство: вся информация о пользователе — на сервере. Клиент держит бессмысленную случайную строку.
   Вариант второй — токен. При логине сервер отдаёт клиенту документ вида «это пользователь такой-то, роль Admin, годен до 14:35», подписанный сервером. На каждом запросе клиент прикладывает документ. 
Сервер проверяет подпись и верит содержимому.
   Ключевое свойство: на сервере не хранится ничего. Никакого списка выданных токенов.
   Выбрал вариант второй, потому что:
Сервер не хранит состояние (Stateless): не нужна база или Redis для проверки сессий.
Быстродействие: валидация подписи идёт в памяти процессора без лишних запросов в БД.
Масштабируемость: любой новый сервер сразу может проверять входящие токены без синхронизации сессий.

	Класс JwtOptions:   
   Issuer и Audience нужны, когда одним ключом пользуются несколько систем: токен от сервиса А не должен приниматься сервисом Б. 
   У нас система одна, и на первый взгляд поля лишние — но проверка aud включена в ASP.NET Core по умолчанию, и отключать её ради экономии двух строк не стоит.
ValidateOnStart() в Program.cs регистрирует валидатор, который прогоняется как часть запуска хоста, до открытия порта. Приложение либо стартует с корректной конфигурацией, либо не стартует вовсе.
Принцип называется fail fast: сломанная конфигурация — ошибка развёртывания, и обнаружиться она должна на развёртывании.
	
	Симметричную(HS256) или Ассиметричную(RS256) подпись — это компромисс между безопасностью и удобством:
   Выбрал Симметричную подпись HS256(означает: один и тот же ключ и подписывает, и проверяет), 
Альтернатива — асимметричная подпись (RS256): приватный ключ подписывает, публичный проверяет, и публичный можно раздавать. Нужна, когда токены выпускает один сервис, а проверяют десять — тогда девяти не надо доверять подпись.
У нас выпуск и проверка в одном процессе, поэтому HS256 достаточно.

	Выбор: JsonWebTokenHandler (вместо устаревшего JwtSecurityTokenHandler).
   Почему именно он:
Без скрытой подмены клеймов (No Claims Mapping): В отличие от старого обработчика, не конвертирует стандартные JWT-имена (sub, role) в длинные legacy-URI из WS-Federation ([http://schemas.xmlsoap.org/.../nameidentifier](http://schemas.xmlsoap.org/.../nameidentifier)). 
	Имена сохраняются 1-в-1, исключая баги, когда User.FindFirst("sub") возвращает null.
	Производительность: Спроектирован с нуля под современный .NET — парсит токены быстрее и производит значительно меньше аллокаций памяти.
	Современный стандарт Microsoft: Является актуальным рекомендуемым API для работы с JWT в современных версиях платформы.

	Singleton вместо Scoped для TokenService:
потому что сервис не имеет изменяемого состояния и зависит только от singleton-зависимостей; плюс переиспользование SymmetricSecurityKey сохраняет внутренний кэш криптопровайдера
Все три поля readonly — это и есть техническое подтверждение потокобезопасности, из которой мы вывели право на singleton.

Сейчас DateTime.UtcNow в TokenService захардкожен, при добавлении тестов заменю на TimeProvider

	Куда девать токен в контракте ответа? Три варианта
   А. Вернуть просто строку токена. Компактно, но контракт нерасширяемый
   Б. { token, user } — токен и данные пользователя рядом.
   В. Только токен, а данные пользователя — отдельным запросом GET api/auth/me.
   Беру Б:
   Возвращаю токен вместе с профилем, чтобы клиенту не нужен был второй запрос и чтобы он не парсил токен ради отображения — токен для клиента непрозрачен
   Фронтенду после логина нужно немедленно показать имя пользователя и решить, рисовать ли админские пункты меню. При варианте В это второй HTTP-запрос сразу за первым, всегда, без исключений. Экономии никакой — данные всё равно понадобятся.

   При логине сервис проверяет пароль через bcrypt, затем TokenService формирует JWT с claims sub, role, jti, подписывает HS256 ключом из User Secrets, время жизни 15 минут из конфигурации

   ## JWT Options: двойное чтение конфигурации в Program.cs
Дата: 19.08.2026
Контекст: Sprint 4B — настройка JwtOptions и JWT Bearer аутентификации.

	Решение
`JwtOptions` читается из конфигурации двумя независимыми способами:
1. `builder.Configuration.GetSection(JwtOptions.SectionName).Get<JwtOptions>()`
   — используется сразу в Program.cs, до builder.Build(), там, где нужна
   готовая переменная (например, для настройки AddJwtBearer через
   TokenValidationParameters).
2. `builder.Services.AddOptions<JwtOptions>().Bind(...).ValidateDataAnnotations().ValidateOnStart()`
   — регистрирует IOptions<JwtOptions> в DI-контейнере, чтобы сервисы
   (TokenService, будущий JwtCurrentUserProvider) могли получить конфиг
   через конструктор, как и любую другую зависимость.

	`Почему не обошлись одним способом`
- Get<T>() не встраивается в DI — сервисы, создаваемые контейнером после
  builder.Build(), не имеют доступа к локальной переменной из Program.cs.
- AddOptions/Bind не может быть использован внутри AddJwtBearer(...), потому
  что тот настраивается ДО builder.Build(), когда ServiceProvider ещё не
  собран и IOptions<T> через DI недоступен.

	`Альтернатива (не реализована)`
- Можно устранить дублирование через IConfigureOptions<JwtBearerOptions>,
получая туда провалидированный IOptions<JwtOptions> из DI. Для масштаба
Argus избыточно — лишний класс ради устранения одной строки кода.

	 `Класс JwtCurrentUserProvider`
  IHttpContextAccessor → HttpContext
  Внедряю IHttpContextAccessor через конструктор — это singleton, живущий всё время работы приложения. Внутри у него AsyncLocal<HttpContext>: специальное хранилище, куда фреймворк в начале каждого запроса кладёт текущий контекст.
  AsyncLocal<T> — переменная, привязанная к логическому потоку выполнения, а не к физическому. Она переживает await: код продолжился на другом потоке из пула — значение осталось прежним.
 `FindFirst("sub")` ищет первый claim с типом "sub". Возвращает Claim? — если такого нет, приходит null.
  Почему <First>: claims — коллекция, и одинаковых типов может быть несколько. Классический пример — пользователь с несколькими ролями: два claim role подряд. У нас роль одна, но метод общий.
  Имя ищем ровно "sub" — потому что в TokenService мы записали именно так, а MapInboundClaims = false запретил обработчику переименовывать claims в длинные URI. Если бы не эта настройка, FindFirst("sub") вернул бы null, а claim лежал бы под именем http://......

	`FallbackPolicy`
  POST api/user (регистрация). Сейчас она анонимная. Регистрация закрывается под админа — поэтому [AllowAnonymous] туда не ставим. 
В будущем, когда появится админский интерфейс, админ сможет создавать пользователей через него. Анонимная регистрация — это потенциальная уязвимость, поэтому закрываем её.
