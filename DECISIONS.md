## RateLimiter (2026-08-02)
Выбран: Fixed Window, partition by IP-адрес.
Почему:
- Защита инфраструктуры от CPU DoS: Каждая проверка через `BCrypt.Verify` сжигает мс. работы CPU. Лимитер отбивает ответом HTTP 429 в Middleware, не доводя запросы до контроллера защищая CPU от истощения
- Совместимость с корпоративным NAT: Порог лимита выставляется с запасом (например, 60 запр/мин на IP), что перекрывает проблему всплесков на границах окон (Burst Boundary) и не мешает легитимным пользователям, сидящим за единым внешним IP.
Отвергнуто:
- Партиционирование по логину: Требует буферизации и парсинга `Request.Body` до контроллера (уязвимость к RAM DoS через тяжелые JSON-пакеты), а также создает уязвимость Self-inflicted DoS (блокировка входа настоящему `admin` путем флуда его логином).
- Sliding Window / Token Bucket: Избыточны по памяти и ресурсам CPU. Для первичного базового забора инфраструктуры усложнение алгоритма не дает преимуществ при адекватно настроенном размере Fixed Window.
- Concurrency Limiter: Отслеживает только одновременные потоки, но свободно пропускает высокий суммарный RPS при быстрых запросах.
