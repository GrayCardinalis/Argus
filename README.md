# Argus

Учёт компьютерной техники и заявок на ремонт для университета.


У вуза есть система для служебных заявок, но она не ведёт учёт самого железа: где стоит, куда переезжало, что в нём меняли. 
Система решает задачу, с которой я сталкиваюсь на работе системным администратором: техника в аудиториях перемещается, ломается и списывается, но её история нигде не фиксируется. 
Argus про это — оборудование по аудиториям, история перемещений, заявки, привязанные к конкретной единице техники, и списание комплектующих со склада.

Argus ведёт оборудование по аудиториям, хранит историю перемещений, принимает заявки на ремонт, поддерживает комментарии и учитывает расход комплектующих со склада.

Одновременно это учебный проект: на нём отрабатывается backend-разработка на ASP.NET Core — аутентификация, работа с БД, обработка ошибок, безопасность.

## Стек

.NET 10, ASP.NET Core Web API, EF Core 10, PostgreSQL, AutoMapper, ErrorOr, BCrypt.Net, JWT (HS256), Scalar

## Что уже работает
- Аутентификация по JWT: access-токен на 15 минут, подпись HS256, ключ хранится вне репозитория
- Роли Client / Technician / Admin с разграничением доступа:
  - справочник пользователей и удаление пользователей — Admin
  - создание, переименование и удаление аудиторий и комплектующих — Admin
  - изменение остатков комплектующих — Admin и Technician
  - создание и списание оборудования — Admin
  - редактирование и перемещение оборудования по аудиториям — Admin и Technician
  - просмотр оборудования, его истории перемещений и техники в аудитории — любой аутентифицированный
- Пользователи: регистрация, редактирование профиля, смена пароля, soft delete с сохранением истории
- Справочники аудиторий и комплектующих
- Ограничение частоты запросов на логин (Fixed Window по IP)
- Бизнес-ошибки через ErrorOr и ApiController, ошибки валидации — ProblemDetails. Для пустых ответов конвейера, включая 401/403, подключён UseStatusCodePages
- Все эндпоинты закрыты по умолчанию (FallbackPolicy)
- Глобальная валидация входных данных через FluentValidation и фильтр действий (RFC 7807 ProblemDetails)
- Оборудование: учёт по инвентарным номерам, списание через статус Recycled, история перемещений по аудиториям с защитой инварианта единственного активного размещения
- Оборудование: полный жизненный цикл (Active / UnderRepair / Recycled), частичный уникальный индекс на активную локацию, история перемещений, получение оборудования аудитории без N+1
- Заявки: создание и карточка, назначение исполнителя, смена статуса, фильтры, комментарии и расход комплектующих
- Общая пагинация списков через PaginationQueryDto, PagedResultDto<T> и ToPagedResultAsync
- Склад: ограничение неотрицательного остатка в БД, транзакционное списание на заявку и защита удаления использованных комплектующих

Наличие кода не означает прохождение интеграционных и конкурентных тестов.

| Метод и маршрут | Назначение | Успешный ответ |
|---|---|---|
| POST /api/supportrequest | Создать заявку | 201, Location и карточка |
| GET /api/supportrequest | Список с фильтрами и пагинацией | 200, страница |
| GET /api/supportrequest/{id} | Карточка заявки | 200, карточка |
| POST /api/supportrequest/{id}/assign-executor | Назначить или заменить исполнителя | 200 без тела |

### Создание и доступ

- Создание доступно активному аутентифицированному пользователю.
  Тело: `title`, `description`, `equipmentId`.
  Автор определяется на сервере, аудитория — по активному размещению оборудования.
  Списанное или неразмещённое оборудование — 409.
- Title ограничен 150 символами, Description — 2000; ограничения есть
  в валидаторах и схеме БД. Status хранится строкой.
  Конфигурация и миграция ConfigureSupportRequestFields опубликованы.
- Admin и Technician читают любую заявку. Остальные роли читают свои заявки.
  Чужая существующая карточка, комментарии и расход возвращают 403, отсутствующая заявка — 404.
- После мягкого удаления клиента или автора комментария история остаётся доступной.
  Вход, справочник пользователей и проверка текущего участника используют запрос ActiveUsers.

### Назначение и статус

- Admin назначает или заменяет активного техника. Technician может взять
  свободную заявку только на себя; перехват заявки другого техника запрещён.
  Повторное назначение себя на уже свою незавершённую заявку — успех без изменений.
- Назначение не меняет статус. В Resolved переназначение запрещено.
  Условный UPDATE проверяет прежнего исполнителя и незавершённый статус;
  конфликт параллельного назначения возвращает 409.
- Статус меняет Admin или назначенный исполнитель. Фактическая смена требует
  назначенного исполнителя. Для незавершённой заявки повтор текущего статуса —
  успех без изменений; из Resolved изменения запрещены, включая повтор Resolved.
- Строгой таблицы переходов нет: между незавершёнными статусами переходы
  свободные, New → Resolved допустим при наличии исполнителя.
- Status и ResolvedAt обновляются одной командой; при закрытии записывается UTC.
  Изменение прочитанных Status или ExecutorId до UPDATE приводит к 409.

### Комментарии

Тело POST: `{ "message": "Неисправность подтверждена" }`.
Автор и время определяются на сервере, внешние пробелы удаляются.
Текст обязателен, максимум 2000 символов проверяет валидатор;
отдельное ограничение длины колонки комментария пока не настроено.
Admin и Technician могут комментировать любую заявку, остальные — свою.
Комментарии разрешены и после Resolved. Сортировка: CreatedAt, затем Id по возрастанию.
Редактирование и удаление комментариев не реализованы.

### Расход компонентов

Тело POST содержит `componentId` и положительное `quantity`.
Admin списывает на любую незавершённую заявку, Technician — только на назначенную ему.

- Проверка заявки и расход выполняются в транзакции ReadCommitted.
  SELECT FOR UPDATE блокирует строку заявки до завершения транзакции,
  координируя списание со сменой статуса и исполнителя.
- Остаток уменьшается условным UPDATE: `quantity >= requestedQuantity`.
  Нехватка — 409, отсутствующий компонент — 404.
- Уменьшение склада и сохранение расхода фиксируются вместе.
  На пару «заявка + компонент» хранится одна строка; повторное списание
  увеличивает Quantity. При переполнении суммарного int возвращается 409.
- Каждый успешный POST — новое списание: повторная отправка не является
  безопасным повтором уже выполненной операции.
- Закрытие заявки само по себе ничего не списывает.
  Возврат компонентов на склад и журнал отдельных списаний не реализованы.
- GET возвращает суммарный расход, отсортированный по Component.Name и ComponentId.
  Физическое удаление компонента допускается только при нулевом остатке
  и отсутствии ссылок из заявок.

`PUT /api/component/{id}/stock` устанавливает новый остаток. Оба поля обязательны.
Пример тела запроса: `{"expectedQuantity":5,"quantity":8}`. Если на складе всё ещё 5,
сервер выставляет 8 и возвращает 204. Если после чтения уже списали деталь,
сервер отвечает 409 Component.StockConflict. Перед новой корректировкой прочитай
текущий остаток через GET /api/component/{id}.

## Пагинация и фильтры

Списочные GET используют общий ответ `PagedResultDto<T>` вместо массива.
Получение одной карточки по id не менялось.

| Параметр | По умолчанию | Ограничение |
|---|---|---|
| Page | 1 | Больше 0 |
| PageSize | 20 | От 1 до 100 |

Значения определены в `Constants/Database/PaginationDefaults.cs`.
Неверные параметры возвращают 400. Страница за пределами списка — 200
с пустым Items и общим TotalCount после фильтров и ограничений доступа.

```json
{
  "items": [],
  "totalCount": 0,
  "page": 1,
  "pageSize": 20
}
```

Пагинация подключена к следующим маршрутам:

- `GET /api/user` — только Admin;
- `GET /api/equipment`;
- `GET /api/auditorium`;
- `GET /api/component`;
- `GET /api/auditorium/{id}/equipment`;
- `GET /api/equipment/{id}/placement-history`;
- `GET /api/supportrequest`;
- `GET /api/supportrequest/{id}/comments`;
- `GET /api/supportrequest/{id}/components`.

В Scalar для следующей страницы увеличьте Page и повторите запрос,
сохранив PageSize и фильтры:
`GET /api/supportrequest?Page=2&PageSize=20`.

Дополнительные фильтры списка заявок: Status, ExecutorId, AuditoriumId,
CreatedFrom, CreatedTo. Заполненные фильтры объединяются через AND.
Граница CreatedFrom включается, CreatedTo исключается; обе даты приводятся к UTC.
Для заявок за 17 ноября по Москве:
`CreatedFrom=2026-11-17T00:00:00+03:00`,
`CreatedTo=2026-11-18T00:00:00+03:00` (в URL знак + кодируется как %2B).
Если обе границы заданы, CreatedFrom должен быть меньше CreatedTo.
Отсутствующий ExecutorId означает отсутствие фильтра, а не «без исполнителя».

Заявки сортируются по CreatedAt и Id по убыванию.
Подсчёт и чтение страницы выполняются отдельными запросами:
при параллельных изменениях TotalCount и Items могут отражать разные моменты,
а записи между последовательными страницами могут смещаться.

## Оборудование

Обновление оборудования разделено на отдельные операции:

- `PUT /api/equipment/{id}` — обновление характеристик карточки,
  доступно Admin и Technician. Обязательны поля `modelName` и
  `ipAddress`; значение `ipAddress: null` очищает адрес.
  Статус оборудования не изменяется.
- `PATCH /api/equipment/{id}/status` — смена рабочего статуса,
  доступна Admin и Technician. Тело содержит только `status`:
  `Active` или `UnderRepair`.
- `DELETE /api/equipment/{id}` — списание, доступно только Admin.
  Устанавливает `Recycled` и закрывает активное размещение.

Редактирование, смена рабочего статуса и перемещение уже списанного оборудования возвращают 409. Повторное списание существующего оборудования возвращает 204.

Прежний `PATCH /api/equipment/{id}` заменён на PUT.

## Запуск

Требуется: .NET 10 SDK, PostgreSQL 15+

1. Установить инструмент EF Core, если его нет:
   dotnet tool install --global dotnet-ef

2. Создать пустую базу `ArgusDb`.

3. Задать секреты (значения свои):
   cd Argus
   dotnet user-secrets init
   dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=127.0.0.1;Port=5432;Database=ArgusDb;Username=postgres;Password=<ваш_пароль>"
   dotnet user-secrets set "Jwt:Key" "<строка не короче 32 символов>"

4. Применить миграции:
   dotnet ef database update

5. Запустить:
   dotnet run

   База после миграций пустая. Создайте пользователя через `POST /api/user`, затем получите токен через `POST /api/auth/login`.

Новый пользователь получает роль Client. Чтобы выдать себе Admin, измените поле `role` в таблице `users` напрямую через update в psql.

Остальные эндпоинты требуют заголовок `Authorization: Bearer <токен>`.
