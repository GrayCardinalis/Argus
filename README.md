# Argus

Учёт компьютерной техники и заявок на ремонт для университета.


У вуза есть система для служебных заявок, но она не ведёт учёт самого железа: где стоит, куда переезжало, что в нём меняли. 
Система решает задачу, с которой я сталкиваюсь на работе системным администратором: техника в аудиториях перемещается, ломается и списывается, но её история нигде не фиксируется. 
Argus про это — оборудование по аудиториям, история перемещений, заявки, привязанные к конкретной единице техники, и списание комплектующих со склада.

Argus ведёт оборудование по аудиториям, хранит историю перемещений, принимает заявки на ремонт и списывает комплектующие со склада при их закрытии.

Одновременно это учебный проект: на нём отрабатывается backend-разработка на ASP.NET Core — аутентификация, работа с БД, обработка ошибок, безопасность.

## Стек

.NET 10, ASP.NET Core Web API, EF Core 10, PostgreSQL, AutoMapper, ErrorOr, BCrypt.Net, JWT (HS256), Scalar

## Что уже работает

- Аутентификация по JWT: access-токен на 15 минут, подпись HS256, ключ хранится вне репозитория
- Роли Client / Technician / Admin
- Пользователи: регистрация, редактирование профиля, смена пароля, soft delete с сохранением истории
- Справочники аудиторий и комплектующих
- Ограничение частоты запросов на логин (Fixed Window по IP)
- Единый формат ошибок — RFC 7807 ProblemDetails
- Все эндпоинты закрыты по умолчанию (FallbackPolicy)

## В работе

Заявки на ремонт, оборудование, история перемещений, валидация через FluentValidation, тесты, Docker.

## Запуск

Требуется: .NET 10 SDK, PostgreSQL 15+

1. Установить инструмент EF Core, если его нет:
   dotnet tool install --global dotnet-ef

2. Создать пустую базу `ArgusDb`.

3. Задать секреты (значения свои):
   cd Argus
   dotnet user-secrets init
   dotnet user-secrets set "ConnectionStrings:DefaultConnection" "Host=127.0.0.1;Port=5432;Database=ArgusDb;Username=postgres;Password=<ваш_пароль>"
   dotnet user-secrets set "Jwt:Key" "<строка не короче 32 символов>"

4. Применить миграции:
   dotnet ef database update

5. Запустить:
   dotnet run

   База после миграций пустая. Создайте пользователя через `POST /api/user`, затем получите токен через `POST /api/auth/login`.

Новый пользователь получает роль Client. Чтобы выдать себе Admin, измените поле `role` в таблице `users` напрямую:

    UPDATE users SET role = 'Admin' WHERE user_name = '<ваш_логин>';

Остальные эндпоинты требуют заголовок `Authorization: Bearer <токен>`.

## Конфигурация

Публичные настройки — в `appsettings.json`, полный набор ключейсо структурой — в `appsettings.Example.json`.
Секреты (строка подключения, ключ подписи) хранятся в User Secrets и в репозиторий не попадают. Обоснование — в `DECISIONS.md`.

## Первый вход

Вариант А — seeding при старте. Приложение при запуске в Development проверяет, есть ли пользователи, и если нет — создаёт админа с известным паролем.
