## Безопасность

### Требования к паролю
Приоритет: высокий

Сейчас проверок нет вообще — пароль из одного символа пройдёт.
Стойкость пароля важнее любых ограничений на число попыток: слабый, пароль подбирается за столько попыток, сколько лимитер сочтёт нормой.

Что сделать (в рамках FluentValidation):
 - минимальная длина 8 -12 символов
 - не длиннее 72 байт — bcrypt молча обрезает всё сверх этого, и остаток пароля просто не участвует в проверке
 - отказ от требований «обязательно цифра и спецсимвол» — они дают Пароль1! вместо длинной фразы; сейчас рекомендуют длину, а не состав

### Блокировка учётки после серии неудачных попыток входа
Приоритет: высокий

Rate limiter по IP защищает CPU, но не защищает конкретный аккаунт: 
	атакующий с пулом адресов перебирает пароль сколько угодно (см. DECISIONS.md).

Что сделать:
 - Считать неудачные попытки на пользователя: `FailedLoginAttempts` и `LockedUntil` в таблице users + миграция
 - После N неудач блокировать вход на время (нарастающая задержка лучше жёсткой блокировки — иначе self -inflicted DoS: флудишь чужим логином и блокируешь человеку вход)
 - Сбрасывать счётчик при успешном входе
 - Ответ при блокировке не должен отличаться от обычного «неверный пароль», иначе он подтверждает существование логина
  
### Логировать неудачные попытки входа
Приоритет: средний

Неудачные входы нигде не фиксируются — распределённый перебор
не оставляет следов. Это предпосылка для любой реакции на атаку.

Что сделать:
 - писать в лог: время, UserName, IP, результат
 - пароль и его хеш в лог не попадают ни при каких условиях
 - ILogger вместо Console.WriteLine


### Динамическая генерация DummyHash для защиты от тайминг -атак
Приоритет: низкий

Сейчас фиктивный хеш `AuthConstants.DummyHash` захардкожен строкой (см. DECISIONS.md). Из -за этого при изменении `work factor` в настройках бэкрипта время проверки для существующих и несуществующих пользователей начнет отличаться, что вернет уязвимость.

Что сделать:
 - Генерировать `DummyHash` при старте приложения через `BCrypt.HashPassword`.
 - Убедиться, что используемый work factor совпадает с боевыми настройками.


### Закрыть регистрацию под админа + seeding первого пользователя
Приоритет: средний

`POST api/user` сейчас анонимный. Argus — внутренняя система: аккаунты должен выдавать администратор, а не заводить любой желающий. 
Плюс каждый вызов сжигает ~100 мс CPU на bcrypt.
Закрыть нельзя, пока нет способа создать первого админа — регистрация требует токена, токен требует пользователя (bootstrap problem).

Что сделать:
 - `Data/DbSeeder.cs`: при старте в Development, если таблица users пуста, создать админа с паролем из `Seed:AdminPassword` (User Secrets, не хардкод)
 - Вызов между `builder.Build()` и `app.Run()`, через `app.Services.CreateScope()`
 — `AppDbContext` scoped, из корневого провайдера его брать нельзя
 - Снять `[AllowAnonymous]` с регистрации
 - Обновить README (раздел «Первый вход») и DECISIONS.md

### Админский сброс пароля
Отдельный эндпоинт `PATCH api/user/{id}/password/reset`, только Admin, без поля CurrentPassword. Сейчас админ вообще не может сбросить чужой пароль — см. DECISIONS.md.

### GET api/user отдаёт всех пользователей любому аутентифицированному
ФИО, email, отделы, роли видит любой Client. Нужен `[Authorize(Roles = "Admin")]` на список и чтение чужих профилей
С открытой регистрацией это фактически публичный справочник сотрудников.

### DeleteAuditoriumAsync и DeleteComponentAsync 
Удаляют физически, через ExecuteDeleteAsync, мимо soft delete. 
В Спринте 6 на аудитории начнёт ссылаться оборудование, и такое удаление либо упадёт ошибкой внешнего ключа, либо утащит связанные записи.
Разобрать в Спринте 6, когда на аудитории начнёт ссылаться оборудование.

## Корректность

### UpdateUserProfileAsync ведёт себя как PUT
Помечен `[HttpPatch]`, но затирает непереданные поля: запрос без `department` обнуляет отдел. Нужен либо `JsonPatchDocument`, либо nullable -обёртки, чтобы отличать «не прислано» от «прислано null».

### Предупреждения EF Core на старте
Глобальный query filter на `User` + обязательные связи в `SupportRequest` и `SupportRequestComment`. 
При фильтрации удалённого пользователя связанные сущности ведут себя непредсказуемо. 
Нужно разобрать при переходе к модулю заявок.

### 503 вместо 500 при недоступности БД
Приоритет: низкий

Сейчас `NpgsqlException` доходит до `UseExceptionHandler` и отдаётся как 500.
5xx различает «я сломался» и «моя зависимость недоступна» — недоступность
базы это 503 Service Unavailable.

Что сделать: отдельный `IExceptionHandler` для `NpgsqlException`,
по аналогии с `UniqueConstraintExceptionHandler`.
